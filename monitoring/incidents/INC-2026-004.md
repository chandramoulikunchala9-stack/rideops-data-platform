## Impact
The `bookings_reject_reasons` check reported 4 rejected bookings instead of 813. The check stayed
in WARN, so a real increase in rejections could have gone unnoticed.

## Detection
During verification of the first full load, 100,000 distinct bookings minus 99,187 loaded minus 4
"rejected" left 809 unexplained rows. An independent query against `core.rejected_records`
showed 813 rejected rows across 4 reasons.

## Root cause
The check used `count(*)` over a subquery that has **one row per reason**, so it counted reasons,
not rejected rows.

## Resolution
Changed the check to `sum(n)`. Added an integration test asserting that core rows plus quarantined
rows equal distinct source keys, so the check is now reconciled against an independent count.

## Lesson
Monitoring needs testing too. Reconcile every metric against an independent calculation at least once.
